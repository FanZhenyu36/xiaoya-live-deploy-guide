# 09 · 排错：先确定哪一层出了问题

回到 [主教程](../README.md)。先读第一条真正的错误，不要只看最后一行的 exit code。

## 1. 快速定位

## 2. 9877 启动卡住

Ubuntu 新开一个终端：

```bash
nvidia-smi
ps -ef | grep -E 'launch_omnivoice|start_flashinfer|omnivoice.cli.demo' | grep -v grep
curl --noproxy '*' --connect-timeout 3 --max-time 5 -I http://127.0.0.1:9877/
```

在首次编译/Graph 捕获期间，网页还没起来是可能的。看前台日志究竟停在下载、权重加载、内核编译还是报错。如果已经打印 traceback，就不是继续等 150 秒能解决的事。

OOM 时先关其他模型，再禁用 Graph 验证；若仍不行，不要删除现有缓存作为第一步。

## 3. Windows 打不开 WSL 服务

1. Ubuntu 内部能否打开 `http://127.0.0.1:9877/`？
2. Windows 能否访问 `127.0.0.1:9877`？
3. 不行时，PowerShell 查 `wsl -d Ubuntu-22.04 hostname -I`，取实际可达的 WSL 地址测试。
4. NAT IP 会变化，不能沿用旧截图中的 `172.x.x.x`。
5. 若只能通过新 WSL IP 访问，在私有配置更新 `tts.omnivoice_base`，然后 reload。

WSL 镜像网络和自动代理支持情况见网络章节，不要用关闭全部防火墙来解决一个本地端口问题。

## 已修复：弹幕回答停在半句话

2026-11-13 实际发现上游 `_llm_collect` 使用 `out.extend(sstream.flush())`，把无句末标点的尾句拆成单字；当 `answer_max_sentences=2` 时，又只保留前两段，导致最后只念一个字或前半句话。逗号短分块也被误当成整句计数。

安装器现在自动应用 `overlays/speech-completion.patch`：按完整句子计数，保留跨流式片段的空格，并将不足 6 字的尾块合并，减少一次额外 TTS。新模板默认 `answer_max_sentences=0`，由提示词控制简短回答，不在播放环节硬截断。

已有服务可以先在设置里把该值设为 0，它可热生效；Python 补丁需要下次正常重启舞台。不要为了生效而中断正在直播的场次。6 项回归测试在 `tests_stage/test_speech_completion.py`，应从已安装工作台的根目录、用其 `.venv` Python 执行；它们使用假 LLM，不加载 GPU、不连接 Vidu。

## 4. TTS 服务返回 WAV 但没听到

HTTP 200、文件字节数、音频时长只证明返回了音频；仍要实际播放。检查文件格式、音量、浏览器输出设备和静音状态。上游旧 smoke 脚本提示 `Play ...` 只是提示你去播放，不一定自动播放。

## 5. 数字人画面慢

把耗时拆开看：

```text
LLM 首字 → 句子积累 → 本地 TTS → 音频转码/上传 → 云端渲染 → RTC 播放
```

本地 Graph 不能提速云端渲染。短句、关闭不必要的思考模式、稳定网络和清晰素材往往更影响体感。不要在没测量前把所有延迟归给显卡。

## 6. 字幕有回复但没有人物声音

先做 `/api/tts/preview`。试听失败则修本地 TTS；试听成功再看喂流、RTC 远端音频订阅、浏览器自动播放和输出设备。不要一开始就重新下载全部模型。

## 7. public 仓库里发现 Key

先到服务方撤销并换新。删当前文件不能撤回 Git 历史和已经被读取的凭据。不要再把新 Key 发到 Issue 或聊天截图里。本仓库的扫描器只是辅助检查，不能保证识别世界上所有密钥格式。

## 8. 反馈问题的最小信息

- Windows / WSL / Python / 显卡版本。
- 主教程第几步，执行的是 PowerShell 还是 Bash。
- 复制的命令（Key 置空）、第一条错误、最后 30–60 行日志。
- 对应端口是否响应，以及是否已有重复实例。

不要把完整 `config.json`、登录凭据、Cookie、私人参考音频或带签名的录播 URL 公开。

## 视频有时停顿、跳帧

先区分：声音正常但画面跳帧，还是声音也停、嘴型跟着停。前者先查 RTC 收流、网络和浏览器解码；后者还要查看本地 TTS 合成是否供得上。不能把首句等待合成的日志等同于播放过程丢帧。

2026-11-14 修复播放器重复绑定：只在订阅成功时绑定，重复成功通知不重置播放器，摄像头和屏幕流不再同时覆盖同一个画面。屏幕流单独发布及断线重连仍受支持。依据 [阿里 ARTC Web 接入说明](https://www.alibabacloud.com/help/en/ims/developer-reference/quick-use)。

在连线结束后刷新舞台页加载修复。关闭重复播放的舞台标签及不需要的视频任务，检查浏览器图形加速，使用稳定网络。代理节点质量和 RTC 网络情况需要在真实连线时检查；不要盲目改模型、升级 SDK 或降低本地素材帧率来解决云端推流卡顿。

## 人物下方出现乱码字幕，但右侧对话正常

先区分网页字幕和生成在视频里的伪文字。网页直接用 `textContent` 显示与右侧相同的回答；这并不代表视频模型生成的字也能正确。

排查时可在本机 `config.json` 的 `session` 中加入 `"send_output_text_to_vidu": false`，再调用 `/api/settings/reload`。新代码会跳过 type10 回复文字上下文，本地字幕及 PCM 喂流保持原流程。注意：这是减少一条云端文字输入的对照试验，**不是 Vidu 官方的字幕关闭参数**，不能承诺消除视频里已经生成的伪字。默认仍为 true，便于兼容及回退；`send_output_per_sentence` 是另一项，勿混改。

若仍有乱码，临时关闭「画面内字幕层 → 显示」：如果乱码依旧可见，说明它已在视频帧内，需要检查形象原素材是否带字、使用干净素材重建形象或向服务方反馈。网页改 UTF-8 或改字体无法抹掉视频像素里的文字。需要画面截图才能进一步确认。

协议参考：[Vidu 组件版详细参数](https://platform.vidu.com/vidu-stream/doc/s2-avatar/component/parameters)。

## 角色突然说“我要睡觉 / 我要下播”

这是回复内容的问题，不等于后台真的挂断。简短人设没有限定持续直播时，模型可能根据人物年龄、晚安话题或旧回答推进睡前剧情；自动闲聊再继承这些上下文，容易持续重复。

2026-11-16 修复：给实际发送给 LLM 的 system 提示加入直播运行规则，普通人设和独立人设都生效；不改写编辑器里保存的人物设定。规则要求不主动宣布睡觉、下播、家长催睡或离开；观众自己告别时可以祝对方晚安，角色仍继续互动。旧的睡觉/下播剧情视为错误上下文，不再沿用。只有主播真正结束连线才是结束，聊天中的起哄不算控制指令。

自动闲聊已把“几点睡”和编造困倦状态的话题换成音乐、小吃等轻松话题。模型输出仍是概率性的，这不是删除所有“晚安”关键词的硬过滤。`llm.broadcast_rules_enabled` 默认 true，可单独配置；更换源码后需要停播重启。若旧剧情已经积累，使用「清空对话记忆」或重启清除临时历史，人设文件不受影响。
